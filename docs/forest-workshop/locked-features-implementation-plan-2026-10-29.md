# 숲결 공방 준비 중 기능 — 구현 설계 및 인수인계

작성: 2026-10-29. 설계 문서이며 구현 완료를 의미하지 않는다. 마지막 원격 확인은 PR #12 병합, main c84680f3다. 구현 시작 시 다시 조회한다. 본 문서는 잠금 기능을 우선 개발하라는 사용자 지시를 반영한다. 기존 전체 UI 개선 계획을 취소하지 않는다.

## 1. 기반과 우선순위

현재 features.ts의 잠금은 9개다. 기억은 서버 원장·인지 주체·공개 범위·정정 상태·출처 ID가 있고 이야기 생성은 공유 기억만 사용한다. 다만 관리 화면·수정 명령은 없다. 이야기 화면의 자동 넘기기는 있으나 설정 기본값은 없다. 페어 지침과 전체 AI 지침, 우편, 조사·순찰, 외부 날씨는 저장·명령·생성 흐름을 새로 연결해야 한다.

순서는 다음과 같다. 같은 묶음은 구현·UI·저장·회귀·설치 검증까지 함께 완료한다. 하나의 PR은 한 묶음을 기본 단위로 한다. PR 병합 상태를 매 작업 시작과 보고 직전에 조회하고 병합된 브랜치를 계속 사용하지 않는다.

| 순서 | 묶음 | 잠금 해제 대상 | 의존성 |
| --- | --- | --- | --- |
| 1 | 이야기 자동 넘기기 기본값 | auto-read | 기존 reader 타이머 |
| 2 | 기억 열람·정정 | memory, pair-memory | 기존 기억 원장·공유 필터 |
| 3 | 전체·페어 AI 지침 | ai-guidelines, pair-guidelines | 기억 범위·프롬프트 검증 |
| 4 | 우편함 | mail | 읽음·보관, 생성 실패·중복 방지 |
| 5 | 조사·순찰 | survey-patrol | 별도 활동 진행·완료 및 우편 연결 |
| 6 | 현실 날씨·날씨 효과 | weather, weather-effects | 도시 조회·캐시·연출 |

기능은 버튼, 실제 저장/조회/명령, 실패 처리, 화면·설치 검증이 모두 연결된 뒤 잠금을 해제한다. 준비 중 버튼을 눌러 다른 준비 중 화면으로 이동시키는 것은 완료가 아니다.

## 2. 화면과 공통 동작

상업게임의 익숙한 목록→선택 상세→행동→목록 복귀를 따른다. 기존 자료의 실제 게임 캡처를 기준으로 설계하되 우편·조사·날씨 화면은 구현 전에 실제 플레이 자료를 추가 확보한다. 홍보 이미지나 기능 설명만으로 화면을 확인했다고 쓰지 않는다.

공통 규칙:
- 목록 위치와 선택, 작성 초안은 실패·재렌더 후 유지한다. 세계 전환 시 다른 세계의 데이터와 섞지 않는다.
- 제목·상태·핵심 수치를 한 곳에 모으고 상세 본문만 별도 영역에서 탐색한다. 주요 저장·닫기 행동은 화면 밖으로 밀리지 않게 한다.
- 44px 이상 터치 영역, 색 이외의 상태 표시, 뒤로 가기 및 포커스 복귀를 제공한다. 잠금 해제 때문에 홈에 버튼 줄을 추가하지 않는다.
- 생성 작업은 비용 발생과 최초 생성 시점을 표시한다. 자동 읽기나 우편 열람이 새 생성 호출을 몰래 시작하지 않는다.

## 3. 묶음별 동작 명세

### A. 이야기 자동 넘기기 기본값

설정의 명칭을 ‘이야기 자동 넘기기’로 명확히 한다. 기본 꺼짐, 간격 4초, 조절 2~10초다. 브라우저 표시 설정으로 저장하며 서버 세계 데이터와 분리한다. 브라우저 저장이 막히면 해당 세션에만 적용한다.

새 이야기를 열 때 기본값을 적용하고 이야기 화면의 기존 자동 버튼으로 이번 읽기만 변경할 수 있다. 배경 탭·기록 창·질문·오류·생성 대기에서 타이머를 멈춘다. 복귀는 사용자가 자동 버튼을 눌러 재개한다. 질문에 임의 답변하지 않고 마지막 장면의 다 읽고 보관은 명시적으로 누르게 한다. 자동 넘기기는 TTS가 아니다.

### B. 기억 관리와 페어 기억 보기

설정 → 기억 관리에서 주민/페어/종류/상태를 고르고 목록과 상세를 연다. 관계 → 기억 보기는 해당 페어와 두 주민이 공유하는 기억을 미리 선택한 같은 화면이다. 목록은 최근순이며 출처 이야기, 발생일, 아는 주민, 사건/감정/플레이어 답변 구분을 표시한다.

세계 소유자의 관리 화면은 전체 원장을 볼 수 있지만 ‘관리자 열람 범위’와 ‘주민 인지 범위’를 명시적으로 구분한다. 페어의 공유 탭은 기존 sharedBy 필터를 재사용한다. 관리 화면에서 봤다는 이유로 해당 기억을 주민 프롬프트에 넣지 않는다.

행동은 정정과 사용 중지/복원이다. 원문 삭제나 덮어쓰기는 제공하지 않는다. 정정은 새 factId를 발급해 supersedes로 원문을 연결하고 원문 상태를 corrected로 바꾼다. 정정문은 원문의 유형·인지 주민·공개 범위·출처를 계승한다. 인지 주민을 늘리거나 비공개를 공개로 바꾸는 기능은 이번 범위에서 제공하지 않는다. 사용 중지는 invalidated로 바꾸고 생성에서 제외한다. 원문 복원은 활성 정정문과 동시에 살아나지 않도록 같은 정정 체인을 검사한다.

문구는 기존 MEMORY_FACT_MAX=160을 사용한다. 원장 상한 1,000건에 도달하면 정정도 실패 이유를 알리고 기존 기억을 자동 삭제하지 않는다. 이미 생성한 이야기 본문은 정정으로 다시 쓰지 않는다.

### C. 전체 및 페어 AI 지침

설정 → AI 지침에서 세계 공통 지침을, 관계 → 지침 관리에서 해당 페어 지침을 편집한다. 사용 여부·본문·마지막 수정 시각·다음 생성부터 적용됨을 표시한다. 기본은 비어 있음/꺼짐. 공통 지침 최대 1,000자, 페어 지침 최대 500자다. 저장·취소·기본값 초기화를 제공하고 초기화는 저장 전 초안 변경이다.

지침은 말투·분위기·관계 진행 속도 같은 서술 선호다. 앱이 강제하는 인지 범위·데이터 접근·보상·형식 검증을 수정하지 않는다. 프롬프트는 앱 규칙→사실/참여자→세계 선호→페어 선호로 구성하고 선호는 신뢰할 수 없는 사용자 입력 블록으로 구분한다. 앱 규칙과 충돌하는 요청은 무시하며, 세계와 페어 선호가 충돌하면 페어 선호를 해당 페어의 서술에 한정 적용한다.

적용 대상은 새 이야기와 새 우편이다. 기존 불변 문서는 유지한다. 프롬프트 버전과 적용 지침 리비전은 생성 manifest에 기록하되 진단 로그에 지침 본문을 노출하지 않는다. 토큰 예산 부족은 규칙을 잘라내지 않고 실패로 처리한다. 지침 변경으로 기억의 인지 범위가 확대되지 않아야 한다.

### D. 우편함

홈 우편 아이콘 → 받은 편지/보관함 → 선택 본문 흐름이다. 아이콘 배지는 안 읽은 편지 수만 나타낸다. 목록에 발신 주민·제목·읽음 상태를, 본문에 내용·날짜와 보관/받은 편지로 이동을 제공한다. 첫 버전에는 첨부 보상·만료·우편 삭제를 두지 않는다.

우편 트리거는 처음부터 모든 생산에 붙이지 않는다. 첫 환영 편지는 고정 내용으로 제공하고, 이후 조사·순찰 완료 결과에서 새 편지를 작성할 수 있게 한다. 결과를 열 때 ‘편지 작성’을 명시적으로 실행해 모델 호출한다. 실패하면 같은 완료 사건으로 재시도하며 사건이나 보상을 재처리하지 않는다. 편지는 한 번 저장되면 임의 재생성하지 않는다.

주민 발신 편지는 그 주민이 아는 기억과 직접 참여한 활동만 참조한다. 발신 주민과 수신 플레이어의 기억을 합쳐 다른 주민 비공개 사실을 전달하지 않는다. 수신/읽음/보관은 서로 다른 상태이며 읽음 처리는 idempotent하다. 목록은 페이지 조회하고 본문은 별도 문서로 저장한다. 백업에 우편 목록과 본문을 포함하며 크기 한도 초과 시 누락된 백업을 성공으로 표시하지 않는다.

### E. 조사·순찰

현재 ‘조사 분야’ 생산과 ‘이야기 탐험’은 유지한다. 잠긴 조사·순찰은 별도 생활 활동으로 설계한다. 조사는 장소를 선택해 짧은 발견을 수집하고, 순찰은 같은 장소의 안부·변화를 확인하는 반복 활동이다. 전투·위험·손실·접속 강제를 도입하지 않는다.

장소 카드→활동 상세에서 참여 주민 1명, 소요 시간, 얻는 기록, 시설 배치 영향을 확인하고 출발한다. 초기 장소는 공방 주변 한 곳, 조사 30분·순찰 15분, 세계당 동시 활동 1개다. 이 수치는 첫 프로토타입 기본값이며 밸런스 검증 전 골드·티켓·물품 보상과 연결하지 않는다. 기능이 없는 보상을 화면에 표시하지 않는다.

참여 주민은 영입된 주민만 선택하며 이야기 탐험 중인 주민과 중복 배정하지 않는다. 출발 시 배치에서 빠지는 처리·시간 계산·취소와 72시간 방치 상한은 기존 탐험 규칙을 재사용하되 이야기 탐험 슬롯을 가로채지 않는다. 취소는 재화 소모 없이 종료한다. 완료 결과는 서버가 저장하고 재접속 후에도 열 수 있어야 한다.

조사는 발견 기록, 순찰은 안부 기록을 남긴다. 최초 결과는 고정 템플릿으로 모델 없이도 완성된다. 주민 편지는 별도 명시적 생성 행동이며 실패해도 활동 완료는 유지한다. 조사에서 생긴 사건을 기억으로 등록할 때는 참여 주민만 인지자로 기록한다.

### F. 현실 날씨와 효과

설정에서 도시를 검색·선택하며 자동 위치 권한은 요청하지 않는다. 첫 버전은 도시 좌표·현지 시간대만 저장하고 상세 주소를 수집하지 않는다. 홈 칩에 선택 도시·날씨·갱신 상태를 표시하고 누르면 상세/도시 변경으로 연결한다.

서버가 제공자 조회·응답 검증·캐시·타임아웃을 담당한다. 새로고침마다 외부 요청을 보내지 않는다. 기본 갱신 간격 30분, 타임아웃 5초이며 실패 시 마지막 성공 시각과 오래된 정보임을 표시한다. 한 번도 성공하지 않았으면 날씨 정보 없음으로 표시하고 게임은 계속 동작한다. 데이터 제공자는 구현 전 이용조건·호출 제한·지역 검색 범위를 확인해 확정한다. API 키가 필요한 서비스는 클라이언트에 키를 넣지 않는다.

날씨 효과는 별도 토글이며 기본 꺼짐. 비·눈·맑음의 가벼운 배경 연출만 제공한다. 도시 현지 시간의 낮/밤과 날씨를 사용하고 현재 수동 계절 선택은 유지한다. 생산 효율·확률·보상·출석에는 영향을 주지 않는다. 모션 감소 또는 비활성 화면에서는 효과를 정지한다. 조회와 효과 설정이 분리돼 효과를 꺼도 날씨 칩은 볼 수 있다.

## 4. 데이터와 명령 설계

기존 트랜잭션·expectedRevision·commandId 재시도 체계를 사용한다. 새 명령을 우회하는 직접 저장을 만들지 않는다.

- 자동 넘기기: localStorage 표시 설정, 구버전/차단 저장소 기본값 제공.
- 기억: 기존 memory 원장을 사용. memory.correct / memory.invalidate / memory.restore는 factId와 필요한 정정문을 받으며 정정 체인·상태를 서버가 검사한다.
- 지침: 세계 설정과 페어별 지침 필드, guidelines.update 명령. 페어 존재와 세계 소속을 검사한다. schema 이행과 구버전 호환 범위를 릴리스 노트에 쓴다.
- 우편: 별도 편지 문서와 세계별 메타데이터/사건 중복키. 목록 조회·본문 조회·생성·읽음·보관 경로를 분리한다. 모델 호출은 저장 트랜잭션 밖에서 하고 저장 시 중복 사건과 세계를 재검사한다.
- 활동: activities.start / cancel / 결과 열람. 서버 시뮬레이션 시간과 완료 사건 ID가 기준이며 클라이언트 카운트다운은 표시 전용이다.
- 날씨: settings.update의 도시 설정과 서버 weather 조회. 외부 캐시는 백업 대상이 아니며 도시 설정은 백업에 포함한다.

큰 우편 본문·기억 페이지 조회는 제한과 정렬이 명시된 cursor 페이지를 사용한다. 각 조회 응답은 세계·요청 순서가 맞는 경우에만 화면에 반영한다. 우편 저장·백업 설계는 기존 문서/트랜잭션 API가 제공하는 원자성을 먼저 확인하고 결정한다.

## 5. 검증과 출시 기준

각 묶음은 다음을 충족한 뒤 새 PR로 올린다.

1. 잠금 위치와 진입 경로를 실제 기능으로 대체하고 주요 상태의 화면을 만든다.
2. 정상·빈 목록·오류·재시도·동시 탭·오래된 응답·세계 전환을 검사한다.

추가 핵심 시나리오:
- 기억/지침: A만 아는 사실이 B가 있는 장면과 B의 편지로 전달되지 않음. 정정 전 원문과 과거 이야기는 유지됨.
- 자동 넘기기: 질문·배경 탭·기록 화면에서 진행하지 않고 마지막 읽음 처리와 보상이 중복되지 않음.
- 우편: 같은 완료 사건의 생성 연속 클릭과 네트워크 재시도에서 문서 1개만 저장됨. 생성 실패가 활동 기록을 지우지 않음.
- 조사/순찰: 이야기 탐험과 주민 중복 배치, UTC 경계, 72시간 초과·시간 역행·취소·동시 완료를 검사함.

## 6. 기본 가정과 결정이 필요한 부분

이 문서의 기본안은 자동 넘기기→기억→지침→우편→조사/순찰→날씨 순서, 날씨는 연출 전용, 우편은 만료·보상 없음, 조사/순찰은 기록 중심이다. 사용자가 원하는 조사·순찰의 목적이 재료 획득 중심이면 E의 보상과 경제 검증 설계를 수정해야 한다. 날씨 제공자와 호출 조건은 외부 공식 자료 조사 후 확정해야 한다. 이를 확인하기 전에 제공자 지원이나 보상 효과를 구현 완료로 보고하지 않는다.
